# 数字化用户选择交互设计

**日期：** 2026-03-21 22:29  
**线路：** Superpowers-only  
**状态：** 设计已确认，待进入 implementation plan

---

## 1. 背景

当前 Superpowers 的多个 skill 在需要用户确认或做选择时，仍大量依赖自然语言输入，例如输入“同意”“可以”之类的文本后再继续。这种交互在 Codex 终端环境下效率较低，尤其是在高频的 brainstorming、plan review、执行分支选择等场景中，会反复打断操作节奏。

同时，现有规则更多停留在“文案层面的数字选项”，没有进一步约束代理在 Codex 中实际调用工具级选择交互。这会导致回答里虽然写了 `1 / 2 / 3`，但界面上并没有真正弹出原生选择框，用户仍然只能手动输入文本，交互体验与预期不一致。

用户希望将这类交互统一优化为“数字选项优先”，尽量让用户通过输入数字完成推进，而不是反复键入自然语言。

需要特别说明的是，用户进一步提出了“单键自动提交”的目标，也就是按下数字键后立即继续、无需再提交输入。根据当前仓库结构，这一目标不属于 skill 文案层的直接控制范围，因而需要拆分为两个阶段处理。

---

## 2. 目标

### 2.1 本次设计目标

1. 在本次纳入范围的所有用户选择交互中，优先输出数字选项，并在非危险、可枚举场景下优先实际调用 `request_user_input`。
2. 推荐项固定放在第 1 项，降低选择成本。
3. 尽量避免要求用户输入自然语言确认。
4. 对无法完全枚举的场景，保留最后一个自由输入兜底项。
5. 在高频 skill 中形成一致的交互风格，减少用户切换成本。
6. 修复“最后一步只写文本提示、不触发选择控件”的退化问题。

### 2.2 非目标

1. 不在本次设计中承诺实现 Codex CLI 的原生单键自动提交。
2. 不修改 Codex 终端输入层、按键捕获逻辑或 TUI 行为。
3. 不承诺修改 Codex 自身的输入层实现。

---

## 3. 需求收敛结果

基于本轮 brainstorming，需求被确认如下：

1. 改动范围不局限于 brainstorming。
2. 本次纳入范围的“需要用户选择”的交互，均应尽量改成数字选择。
3. 各个场景的选项文案可以按语义定制，不要求机械统一成“同意/不同意”。
4. 默认保留最后一个自由输入兜底项，例如“输入其它意见或要求”。
5. 真正的“单键自动提交”作为第二阶段目标处理。
6. 非危险、可枚举选择不能只停留在普通文本里，应优先触发 `request_user_input`。
7. 可枚举危险操作改为“两段枚举确认优先”，两个阶段都使用数字选项，并将第二段的最终确认放在第 2 项，而不是默认手输确认词。
8. 如果某些场景仍必须文本输入，问题中必须直接展示精确输入文本，方便复制粘贴。

---

## 4. 方案概览

本次采用“一处定规则，多处做落地”的方案。

### 4.1 全局规则入口

在 `skills/using-superpowers/SKILL.md` 中新增明确规则：

- 只要轮到用户做选择，优先提供数字选项。
- 非危险、可枚举选择优先实际调用 `request_user_input`，而不只是输出 `1 / 2 / 3` 文本。
- 推荐项排在第 1 项。
- 尽量将选项数量控制在 2 到 4 项。
- 场景允许时，在最后一项提供自由输入兜底。
- 避免开放式问题，例如 “Which approach?”、“What would you like to do?”。
- 危险、可枚举选择优先采用两段数字确认：第一段数字选项，第二段仍为数字选项，并将最终确认放在第 2 项。
- 如果确实仍需文本确认，必须在问题里直接展示精确输入文本。

这条规则作为上游约束，指导后续所有 skill 的提问方式。

### 4.2 重点落地文件

优先修改以下 skill：

- `skills/brainstorming/SKILL.md`
- `skills/writing-plans/SKILL.md`
- `skills/executing-plans/SKILL.md`
- `skills/finishing-a-development-branch/SKILL.md`

其职责划分如下：

#### `skills/brainstorming/SKILL.md`

负责将以下场景改为数字化选择优先：

- 澄清问题中的选择题
- 设计分段确认
- 设计文档 review 后是否继续

#### `skills/writing-plans/SKILL.md`

负责将以下场景改为数字化选择优先：

- plan 完成后的执行方式选择
- 需要用户确认下一步计划方向的场景

#### `skills/executing-plans/SKILL.md`

负责将以下场景改为数字化选择优先：

- 遇到 blocker 后的求助问题
- 计划存在疑问时的澄清问题

#### `skills/finishing-a-development-branch/SKILL.md`

该 skill 当前已具备编号选项基础。本次重点是在保持主流程结构的前提下，补充工具级弹窗要求，并把危险操作从“typed confirmation 默认方案”调整为“两段数字确认优先”，同时将第二段的最终确认从第 1 项移到第 2 项以降低误触。

### 4.3 本次实施范围与完成边界

本次实现范围定义如下：

1. **强制落地文件**
   - `skills/using-superpowers/SKILL.md`
   - `skills/brainstorming/SKILL.md`
   - `skills/writing-plans/SKILL.md`
   - `skills/executing-plans/SKILL.md`
   - `skills/finishing-a-development-branch/SKILL.md`
   - `docs/README.codex.md`
   - `tests/prompt-contracts/test-numeric-choice-interactions.sh`

2. **覆盖目标**
   - 所有在以上 skill 中出现的“下一步 / 是否继续 / 选择方案 / 选择执行方式 / blocker 求助 / 结束分支处理”类可枚举选择
   - 以上范围内的危险操作确认流程

3. **不在本次直接改动范围**
   - 未列出的其它 skill 文档
   - Codex 输入层本身
   - 真实 raw key 自动提交能力

4. **完成判定**
   - 上述强制落地文件全部更新
   - prompt-contract 测试覆盖新增规则
   - 完成第 7 节定义的 3 类真实会话级 smoke test，证明“最后一步”不再只停留在文本提示，而是实际触发 `request_user_input`
   - 为每个 smoke test 保留可审计证据，其中工具调用记录 / transcript 为必选证据

## 5. 交互规范

### 5.1 审批类场景

例如：

- 是否认可当前设计段落
- 是否继续下一阶段
- 是否认可当前文档内容

推荐使用如下结构：

```text
请选择下一步：

1. 同意并继续
2. 提修改意见
3. 输入其它意见或要求
```

如果该场景可枚举且不属于危险操作，应优先通过 `request_user_input` 实际弹出选择，而不是只在普通文本里列出数字。

### 5.2 非审批类场景

例如：

- 选择实现路线
- 选择执行方式
- 选择分支处理方式

推荐使用如下结构：

```text
请选择下一步：

1. <推荐方案>
2. <备选方案>
3. <其它常见方案>
4. 输入其它意见或要求
```

对“是否继续下一步”“是否进入某个已知流程”“是否继续测试/计划/交接”这类高频收尾问题，默认应直接触发 `request_user_input`，不接受“如果你要继续，请回复 1/2/3”这种弱实现。

### 5.3 兜底规则

1. 能枚举则优先枚举。
2. 不强制所有场景都保留自由输入项，但默认应保留。
3. 在**非危险确认流程**中，当用户直接输入文字时，仍应视为有效反馈，而不是报错。
4. 在**危险确认流程**中，除非已进入明确的文本回退模式，否则自由文本不视为最终确认指令；应将其解释为补充反馈或求助信号，并重新发起当前确认步骤。

### 5.4 危险操作确认

以下场景仍需要明确的二次确认，以避免误触：

- 删除分支
- 丢弃工作
- 任何可能造成不可逆损失的操作

推荐的默认结构如下：

```text
第一步：进入危险确认

1. 确认并进入下一步
2. 取消
3. 自由输入
```

```text
第二步：最终确认

1. 取消并返回上一步
2. 最终确认
3. 自由输入
```

说明：

1. 第一段和第二段都优先使用 `request_user_input`。
2. 两段都继续使用数字选项，避免第二段依赖 `a / b / c` 这类输入层热键。
3. 第二段将“取消并返回上一步”放在第 1 项，将“最终确认”放在第 2 项，以降低误触最终执行的概率。
4. 不要求默认手输 `discard`、`confirm` 一类确认词。
5. 第一步中的“取消”必须回到**进入危险确认之前的直接父流程**；如果不存在可恢复的父流程，则以“已取消危险操作，未执行任何变更”结束当前危险子流程。
6. 第二步中的“取消并返回上一步”必须回到第一步，而不是直接执行或结束。
7. 两个步骤中的“自由输入”都只作为补充反馈或求助入口；处理完反馈后必须重新发起当前步骤，不得执行、不得取消。
8. 只有当 `request_user_input` 在该环境不可用，或确认内容必须依赖唯一文本令牌时，才允许回退到文本输入。
9. 回退到文本输入后，仍必须保持“两段确认语义”：
    - 第一步要求用户输入 `1` / `2` / `3`
    - 第二步要求用户输入 `1` / `2` / `3`
    - 只有当业务语义确实要求唯一文本令牌时，第二步才允许改为输入精确确认词
10. 一旦进入文本回退模式，问题中必须直接展示可复制的精确输入内容；如果只是普通自由文本，不能被当作最终确认。
11. 在文本回退模式下，如果用户输入非法 token、空输入或其它非预期文本，系统必须：
    - 明确提示本步允许的合法输入
    - 保持在当前确认步骤，不得自动前进、不得自动执行、不得默认取消
    - 重新展示当前步骤的合法选项
12. 在文本回退模式下，只有当用户输入当前步骤定义的合法 token 时，才允许发生状态迁移。

可以将危险确认抽象为以下状态机：

```text
Parent Flow
  └─> Danger Step 1
        ├─ 1: 进入 Danger Step 2
        ├─ 2: 返回 Parent Flow / 若无父流程则取消结束
        └─ 3: 补充反馈 / 求助 -> 回到 Danger Step 1

Danger Step 2
  ├─ 1: 返回 Danger Step 1
  ├─ 2: 执行危险操作
  └─ 3: 补充反馈 / 求助 -> 回到 Danger Step 2

Text Fallback Mode
  ├─ valid token: 按对应状态迁移
  └─ invalid / empty / unexpected: 留在当前步骤并重试
```

## 6. 阶段拆分

### 阶段 1：Superpowers 仓库内可控改动

目标：

- 让所有高频选择型交互输出数字选项
- 让用户尽量通过工具级弹窗和短输入推进流程
- 让可枚举危险操作采用两段枚举确认，减少手输成本

结果：

- 用户交互从“输入自然语言确认”收敛为“输入数字选择”
- 显著减少终端中的文字输入量
- 修复“写了选项却没有真实弹框”的体验断层

### 阶段 2：Codex 输入层可行性评估

目标：

- 评估是否可以实现真正的“按下数字键立即提交”

这需要单独确认：

- Codex CLI 是否支持 raw key 捕获
- 是否存在可插入的输入层 hook 或 wrapper
- 该能力是否应放在 Superpowers 之外实现

本阶段不属于当前仓库 skill 文案改动的直接交付范围。

## 7. 测试策略

本次设计建议至少覆盖以下验证点：

1. `brainstorming` 场景下，不再要求用户输入“同意”“可以”等自然语言。
2. 高频选择场景默认输出数字选项，并在非危险、可枚举情况下优先触发 `request_user_input`。
3. 推荐项位于第 1 项。
4. 危险操作默认采用两段枚举确认，而不是直接手输确认词。
5. 文档明确区分：
   - 当前仓库负责“数字化选项”和工具级交互约束
   - 单键自动提交属于后续独立工作线
6. 如果某处仍保留文本输入，文案必须直接展示精确输入文本。
7. “最后一步 / 下一步 / 是否继续”这类收尾问题，必须以实际调用 `request_user_input` 作为硬性验收项，不能只停留在普通文本中的 `1 / 2 / 3`。
8. prompt-contract 测试必须包含能识别“弱实现”的断言，例如禁止“如果你要继续，请回复 1/2/3”一类仅文本提示的模式。
9. 真实会话级 smoke test 至少覆盖以下 3 类场景：
   - 一个**非危险收尾场景**：验证“最后一步 / 下一步”真实触发 `request_user_input`
   - 一个**多题连续选择场景**：验证连续弹框不会退化成纯文本
   - 一个**危险操作二段确认场景**：验证两段都使用数字，且第二段的最终确认位于第 2 项
10. smoke test 的通过证据必须包含：
   - 会话 transcript / 工具调用记录，能证明实际调用了 `request_user_input`
11. smoke test 的补充证据建议包括其一或全部：
   - UI 截图
   - 人工观察记录
   - 相关测试说明文档
12. 对本次纳入范围的每个强制落地 skill，至少要有一个对应的验收映射：文件 -> 场景 -> 断言方式（prompt-contract / smoke test / 人工验证）。

以上 1-12 为本次设计的**硬性验收标准**。

建议同时补充与 skill 输出约束相关的回归测试，避免后续 prompt 漂移后重新退回开放式问题。

## 8. 风险与权衡

### 8.1 风险

1. 即使强制优先使用 `request_user_input`，仍不能从根本上保证 Codex 真正实现“单键自动提交”。
2. 某些 skill 已经存在固定格式要求，修改时需要避免破坏原有流程约束。
3. 如果选项过多，虽然是数字化，也会降低可读性和选择效率。
4. 将危险确认从手输改成两段枚举后，需要确保第二段的区分度足够明显，避免用户误把第一段当最终确认。

### 8.2 权衡

1. 优先实现“工具级数字选择优先”，因为这是当前仓库可控且高收益的部分。
2. 保留自由输入兜底，兼顾效率与灵活性。
3. 危险操作采用两段枚举确认，在不依赖手输的前提下保留防误触能力。

---

## 9. 结论

本次设计确定采用以下方向：

1. 在 Superpowers 内建立“数字选项优先”的统一交互规范。
2. 在高频 skill 中按场景落地，不做僵硬统一文案。
3. 默认保留最后一个自由输入兜底项。
4. 非危险、可枚举选择优先通过 `request_user_input` 落地为真实弹窗，而不是停留在文案层。
5. 危险操作默认采用“两段枚举确认”，只在极少数必要场景下保留可复制的文本确认。
6. 将“单键自动提交”拆分为后续 Codex 输入层独立课题。

这套设计可以在不触碰 Codex CLI 输入机制的前提下，先显著提升当前终端工作流的交互效率，并修复“写了数字选项却没有真实弹框”的关键体验缺陷。
