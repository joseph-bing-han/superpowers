# 数字化用户选择交互设计

**日期：** 2026-03-21 22:29  
**线路：** Superpowers-only  
**状态：** 设计已确认，待进入 implementation plan

---

## 1. 背景

当前 Superpowers 的多个 skill 在需要用户确认或做选择时，仍大量依赖自然语言输入，例如输入“同意”“可以”之类的文本后再继续。这种交互在 Codex 终端环境下效率较低，尤其是在高频的 brainstorming、plan review、执行分支选择等场景中，会反复打断操作节奏。

用户希望将这类交互统一优化为“数字选项优先”，尽量让用户通过输入数字完成推进，而不是反复键入自然语言。

需要特别说明的是，用户进一步提出了“单键自动提交”的目标，也就是按下数字键后立即继续、无需再提交输入。根据当前仓库结构，这一目标不属于 skill 文案层的直接控制范围，因而需要拆分为两个阶段处理。

---

## 2. 目标

### 2.1 本次设计目标

1. 在所有需要用户做选择的交互场景中，优先输出数字选项。
2. 推荐项固定放在第 1 项，降低选择成本。
3. 尽量避免要求用户输入自然语言确认。
4. 对无法完全枚举的场景，保留最后一个自由输入兜底项。
5. 在高频 skill 中形成一致的交互风格，减少用户切换成本。

### 2.2 非目标

1. 不在本次设计中承诺实现 Codex CLI 的原生单键自动提交。
2. 不修改 Codex 终端输入层、按键捕获逻辑或 TUI 行为。
3. 不改变高风险操作的明确确认机制。

---

## 3. 需求收敛结果

基于本轮 brainstorming，需求被确认如下：

1. 改动范围不局限于 brainstorming。
2. 所有“需要用户选择”的交互，均应尽量改成数字选择。
3. 各个场景的选项文案可以按语义定制，不要求机械统一成“同意/不同意”。
4. 默认保留最后一个自由输入兜底项，例如“输入其它意见或要求”。
5. 真正的“单键自动提交”作为第二阶段目标处理。

---

## 4. 方案概览

本次采用“一处定规则，多处做落地”的方案。

### 4.1 全局规则入口

在 `skills/using-superpowers/SKILL.md` 中新增明确规则：

- 只要轮到用户做选择，优先提供数字选项。
- 推荐项排在第 1 项。
- 尽量将选项数量控制在 2 到 4 项。
- 场景允许时，在最后一项提供自由输入兜底。
- 避免开放式问题，例如 “Which approach?”、“What would you like to do?”。

这条规则作为上游约束，指导后续所有 skill 的提问方式。

### 4.2 重点落地文件

优先修改以下 skill：

- `skills/brainstorming/SKILL.md`
- `skills/writing-plans/SKILL.md`
- `skills/executing-plans/SKILL.md`
- `skills/finishing-a-development-branch/SKILL.md`

其职责划分如下：

#### `skills/brainstorming/SKILL.md`

负责将以下场景改为数字化选择优先：

- 澄清问题中的选择题
- 设计分段确认
- 设计文档 review 后是否继续

#### `skills/writing-plans/SKILL.md`

负责将以下场景改为数字化选择优先：

- plan 完成后的执行方式选择
- 需要用户确认下一步计划方向的场景

#### `skills/executing-plans/SKILL.md`

负责将以下场景改为数字化选择优先：

- 遇到 blocker 后的求助问题
- 计划存在疑问时的澄清问题

#### `skills/finishing-a-development-branch/SKILL.md`

该 skill 当前已具备编号选项基础。本次重点是保持风格一致，并补充全局规则对齐说明，而不是大幅重写已有四选项结构。

---

## 5. 交互规范

### 5.1 审批类场景

例如：

- 是否认可当前设计段落
- 是否继续下一阶段
- 是否认可当前文档内容

推荐使用如下结构：

```text
请选择下一步：

1. 同意并继续
2. 提修改意见
3. 输入其它意见或要求
```

### 5.2 非审批类场景

例如：

- 选择实现路线
- 选择执行方式
- 选择分支处理方式

推荐使用如下结构：

```text
请选择下一步：

1. <推荐方案>
2. <备选方案>
3. <其它常见方案>
4. 输入其它意见或要求
```

### 5.3 兜底规则

1. 能枚举则优先枚举。
2. 不强制所有场景都保留自由输入项，但默认应保留。
3. 当用户直接输入文字时，仍应视为有效反馈，而不是报错。

### 5.4 危险操作例外

以下场景继续保留强确认文本，不改为“一键继续”：

- 删除分支
- 丢弃工作
- 任何可能造成不可逆损失的操作

这样可以保持与现有安全约束一致，避免误触。

---

## 6. 阶段拆分

### 阶段 1：Superpowers 仓库内可控改动

目标：

- 让所有高频选择型交互输出数字选项
- 让用户尽量通过输入数字推进流程

结果：

- 用户交互从“输入自然语言确认”收敛为“输入数字选择”
- 显著减少终端中的文字输入量

### 阶段 2：Codex 输入层可行性评估

目标：

- 评估是否可以实现真正的“按下数字键立即提交”

这需要单独确认：

- Codex CLI 是否支持 raw key 捕获
- 是否存在可插入的输入层 hook 或 wrapper
- 该能力是否应放在 Superpowers 之外实现

本阶段不属于当前仓库 skill 文案改动的直接交付范围。

---

## 7. 测试策略

本次设计建议至少覆盖以下验证点：

1. `brainstorming` 场景下，不再要求用户输入“同意”“可以”等自然语言。
2. 高频选择场景默认输出数字选项。
3. 推荐项位于第 1 项。
4. 危险操作仍保留文本强确认。
5. 文档明确区分：
   - 当前仓库负责“数字化选项”
   - 单键自动提交属于后续独立工作线

建议优先补充与 skill 输出约束相关的回归测试，避免后续 prompt 漂移后重新退回开放式问题。

---

## 8. 风险与权衡

### 8.1 风险

1. 仅修改 skill 文案，不能从根本上保证 Codex 真正实现“单键自动提交”。
2. 某些 skill 已经存在固定格式要求，修改时需要避免破坏原有流程约束。
3. 如果选项过多，虽然是数字化，也会降低可读性和选择效率。

### 8.2 权衡

1. 优先实现“数字选择优先”，因为这是当前仓库可控且高收益的部分。
2. 保留自由输入兜底，兼顾效率与灵活性。
3. 危险操作继续保留强确认，优先安全性而非极致快捷。

---

## 9. 结论

本次设计确定采用以下方向：

1. 在 Superpowers 内建立“数字选项优先”的统一交互规范。
2. 在高频 skill 中按场景落地，不做僵硬统一文案。
3. 默认保留最后一个自由输入兜底项。
4. 危险操作继续保留明确文本确认。
5. 将“单键自动提交”拆分为后续 Codex 输入层独立课题。

这套设计可以在不触碰 Codex CLI 输入机制的前提下，先显著提升当前终端工作流的交互效率。
