## Context

当前仓库已经部分采用了更稳定的 agent 交互方式，例如 `request_user_input`、stream-json 日志和 transcript 解析；但仍有多处 workflow 与测试直接依赖助手的自由文本输出。典型问题包括：

- 通过 `grep` 或正则匹配 verdict 文案、关键词或固定措辞来判断流程是否正确
- 验证“模型说了什么”，而不是“模型做了什么”
- 依赖中文或英文的固定短语来判断通过、继续、审核失败等状态

这类设计在模型升级、供应商切换、语言偏好变化或 prompt 调整后容易失稳。对于当前仓库，这种不稳定不仅影响测试结果，还会影响对 skill 行为的长期维护与回归验证。

本次设计面向跨模块治理，覆盖 `skills/`、`tests/` 与相关文档，目标是在不牺牲自然语言表达灵活性的前提下，为关键 workflow 建立稳定、可验证、可迁移的协议层。

## Goals / Non-Goals

**Goals:**

- 将关键 workflow 的机器判定依据从自由文本措辞迁移到工具事件、transcript 事件与固定枚举状态
- 为 reviewer、workflow checkpoint、execution handoff 等高价值节点建立统一协议面
- 明确“prose 负责表达，协议负责判定”的边界
- 将高脆弱度测试迁移到 transcript / structured signal 断言
- 增加语言漂移与模型漂移下的稳定性验证能力

**Non-Goals:**

- 不要求将所有中文文案统一改写为英文
- 不要求所有 prompt 或 skill 正文改成固定模板全文输出
- 不试图一次性重写所有测试与文档
- 不修改外部平台本身的 UI / input layer 行为
- 不把现有文档措辞一致性问题视为本次改造的主要目标

## Decisions

### 1. 将协议层与表达层显式分离

关键技术决策是把当前输出分成两层：

- 协议层：供机器读取与自动化验证的稳定信号
- 表达层：供用户阅读的自然语言正文

协议层优先级如下：

1. 工具调用事件
2. transcript / stream-json 中的结构化事件
3. 固定机器可读尾块
4. 自然语言正文

选择这个顺序的原因是：越靠前的信号越不依赖措辞，跨模型稳定性越高。相比之下，直接用 prose 作为协议虽然实现成本低，但长期维护成本最高。

备选方案：
- 继续扩展中英双语 regex：短期便宜，但无法根治模型漂移
- 强制固定自然语言全文模板：对模型约束过重，且仍可能因格式波动失效

### 2. 统一关键 workflow 的最小枚举集合

对关键节点统一定义固定枚举，而不是让每个 skill 各自发明 verdict 文案。

建议统一的协议字段包括：

- `workflow_state`
- `review_verdict`
- `task_status`
- `next_action`

这些字段的取值使用简短、稳定、易解析的英文枚举 token。这样做的原因不是偏向英文表达，而是为了降低 token 歧义、简化日志解析，并提升跨语言复用性。

备选方案：
- 中文枚举 token：可行，但与现有 transcript / tool / harness 生态衔接较弱
- 中英双 token 并存：会提高解析复杂度与维护成本

### 3. 优先改“行为断言”，延后改“文案优化”

本次迁移将优先替换最脆弱的测试：

- 直接匹配固定 verdict 文案
- 直接匹配模型复述 skill 的关键词
- 通过自由文本判断是否执行了某个 workflow 动作

优先把这些断言迁移为：

- 验证是否发生了预期工具调用
- 验证 transcript 中是否存在预期状态字段
- 验证固定尾块是否输出了稳定协议

这样可以先解决真正的失效风险，再决定是否继续优化文档与提示词表述。

### 4. 对不同 workflow 采用不同协议载体

不是所有流程都必须输出 JSON。

本次设计选择按场景区分：

- 对已有工具事件的流程，直接以工具事件为真相源
- 对 transcript 中已有结构化字段的流程，以 transcript 为真相源
- 对纯自然语言 reviewer / handoff 场景，补充固定尾块作为协议面

这样做比“一刀切全部改成 JSON”更符合当前仓库现状，也更容易分阶段实施。

### 5. 把语言漂移验证纳入正式回归面

在完成协议层迁移后，新增一类专门回归：

- 中文输出
- 英文输出
- 不指定语言
- 简洁风格
- 详细风格

这些变体只检查协议层是否保持一致，不检查 prose 是否完全一致。这样可以确保未来模型升级时，仓库验证体系仍然围绕稳定行为而不是表述习惯运转。

## Risks / Trade-offs

- [协议设计过宽，字段太多] → 先收敛最小枚举集合，只覆盖关键 workflow，再按需要扩展
- [部分旧测试短期内同时依赖新旧两套判定方式] → 分阶段迁移，先让新协议成为主判定依据，再删除旧 prose 匹配
- [不同平台 transcript 能力不完全一致] → 优先使用各平台共有的工具事件与最小结构块，平台差异放入实现层适配
- [团队继续把 prose 当作临时协议] → 在 specs 中明确禁止“自由文本作为唯一机器契约”
- [过度追求结构化导致 prompt 可读性下降] → 仅在关键节点追加协议面，不重写正文叙述结构

## Migration Plan

1. 盘点仓库中依赖自由文本的测试与 workflow 断言点，按脆弱度分级
2. 定义统一协议字段、枚举值与适用节点
3. 为关键 workflow 增加协议面，优先使用工具事件与 transcript 字段，必要时补固定尾块
4. 将高脆弱度测试迁移为基于事件 / 状态 / 结构块的断言
5. 增加语言漂移回归验证，确认协议在不同输出风格下保持稳定
6. 在协议迁移完成后，逐步删除冗余的 prose 匹配逻辑

回滚策略：

- 保留旧测试脚本的最小可回退版本，直到新协议断言稳定
- 若某一类协议面在某平台不可用，可临时退回固定尾块，但不退回自由 prose 匹配

## Open Questions

- reviewer 与 implementer 的固定尾块是否统一为纯文本枚举，还是允许 JSON 作为更强结构
- 不同平台 transcript 的最小公共字段集合应如何定义，才能避免平台特化过重
- prompt-contract 测试是否继续承担“文档契约存在性”职责，还是进一步细化为“文档契约 + 行为契约”双层验证
